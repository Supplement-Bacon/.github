## Versioning

Every workflow here runs with the calling repository's secrets, so what a tag
points at matters. Two kinds of tag:

| Tag | Mutability | Use it when |
| --- | --- | --- |
| `vX.Y.Z` (e.g. `v3.0.1`) | **Immutable.** Never moved, never deleted, by anyone. | You want the exact same CI on every run |
| `vX` (e.g. `v3`) | **Moving pointer**, repointed to the newest `vX.Y.Z` of that major | You want patches and minors automatically |

```yaml
uses: Supplement-Bacon/.github/.github/workflows/phpunit.yml@v3      # follows 3.x
uses: Supplement-Bacon/.github/.github/workflows/forge.yml@v3.0.1    # frozen
```

A **major is never adopted automatically**: `v3` will never start pointing at a
`v4.x.y`. Moving to a new major is always an explicit edit in the calling
repository.

Never pin `@main`. It is unreleased code, and it reaches production pipelines on
the next run with no review on the consumer's side.

### How a release happens

Releases are cut by [release-please](https://github.com/googleapis/release-please)
from the [Conventional Commits](https://www.conventionalcommits.org/) landed on
`main`:

1. A commit lands on `main`. `fix:` schedules a patch, `feat:` a minor, and
   `feat!:` or a `BREAKING CHANGE:` footer a major.
2. release-please opens or updates a **Release PR** carrying the next version
   and its changelog.
3. Merging that Release PR *is* the release: it creates the immutable `vX.Y.Z`
   tag, publishes the GitHub Release, and repoints `vX` at it.

Nothing reaches consumers until that Release PR is merged. Merging to `main`
alone changes nothing for them.

Both tag classes are enforced by organization rulesets, not convention. A
released tag cannot be moved or deleted even by an organization owner; doing so
requires editing the ruleset, which leaves an audit trail.

## Repository Structure

```text
.github/
├── CODEOWNERS                      # Ownership of the sensitive paths below
├── actions/
│   └── setup-php-and-dependencies/ # Composite action — PHP, Composer & private Git auth
│       └── action.yml
└── workflows/
    ├── codeowners-validation.yml   # Validates the caller's CODEOWNERS file
    ├── forge.yml                   # Deploy via Laravel Forge
    ├── frontend-lib-ci.yml         # Format & lint for frontend libraries
    ├── laravel-pint.yml            # PHP code formatting with Laravel Pint
    ├── model-coverage.yml          # Model factory coverage reporting
    ├── phpunit.yml                 # PHPUnit tests & coverage
    ├── sonarqube.yml               # SonarCloud analysis & PR comment
    ├── release.yml                 # This repository's own releases (not reusable)
    └── self-ci.yml                 # This repository's own CI (not reusable)

CHANGELOG.md                        # Generated by release-please
version.txt                         # Current version, source of truth for release-please
release-please-config.json
.release-please-manifest.json
profile/README.md                   # Organization profile page
```

`release.yml` and `self-ci.yml` are **not** reusable — they run on this
repository only. Everything else is `workflow_call`.

## Reusable Workflows

All workflows are triggered via `workflow_call` and are designed to be called from other repositories in the organization.

### Laravel Pint

> `.github/workflows/laravel-pint.yml`

Automatically formats PHP code with [Laravel Pint](https://laravel.com/docs/pint).

| Input                   | Type     | Required | Default | Description                                                            |
| ----------------------- | -------- | -------- | ------- | ---------------------------------------------------------------------- |
| `composer_repositories` | `string` | ❌       | `""`    | Newline-separated private repositories needed during Composer install  |
| `extra_owner`           | `string` | ❌       | `""`    | Optional second owner (organization/user) for additional private repos |
| `extra_repositories`    | `string` | ❌       | `""`    | Newline-separated repositories for `extra_owner`                       |

- Uses the **Setup PHP And Dependencies** composite action to install PHP & Composer.
- On a **pull request**: runs Pint in fix mode and automatically commits formatting fixes via `stefanzweifel/git-auto-commit-action`.
- On a **push**: runs Pint in check mode (`--test`) and fails if formatting is not compliant.

### PHPUnit

> `.github/workflows/phpunit.yml`

Runs PHPUnit tests with coverage handling.

Inputs:

- `composer_repositories` (`string`, optional, default: `""`) — Newline-separated private repositories needed during Composer install.
- `test-args` (`string`, optional, default: `--parallel --processes=4 --colors=never`) — Arguments passed to PHPUnit.
- `run-example-tests` (`boolean`, optional, default: `false`) — If `true`, skips standard PHPUnit jobs so example-only test workflows can run instead.
- `run-phpunit-coverage` (`boolean`, optional, default: `true`) — If `true`, enables the `phpunit-coverage` job on pull requests.
- `extra_owner` (`string`, optional, default: `""`) — Optional second owner (organization/user) for additional private repos.
- `extra_repositories` (`string`, optional, default: `""`) — Newline-separated repositories for `extra_owner`.

**2 jobs are defined:**

1. **phpunit** — Runs the full test suite with coverage (`pcov`), then uploads `coverage.xml` as an artifact.
2. **phpunit-coverage** — On pull requests, checks out the base branch and generates a reference coverage report (`coverage-base.xml`) used for SonarQube comparison.

### SonarQube

> `.github/workflows/sonarqube.yml`

Runs [SonarCloud](https://sonarcloud.io/) analysis and posts a coverage comment on pull requests.

- No workflow input is required.

- Downloads coverage artifacts generated by the **PHPUnit** workflow (PR + base).
- Runs SonarCloud scan via `SonarSource/sonarqube-scan-action`.
- Parses Clover reports to compute coverage diffs (statements, hits, misses, files).
- Fetches SonarCloud quality metrics (bugs, vulnerabilities, code smells, duplications).
- Creates or updates a summary comment on the PR with the full report.

### Model Coverage

> `.github/workflows/model-coverage.yml`

Reports which Eloquent models have no factory, and posts the result as a pull
request comment.

| Input                   | Type     | Required | Default | Description                                                            |
| ----------------------- | -------- | -------- | ------- | ---------------------------------------------------------------------- |
| `composer_repositories` | `string` | ❌       | `""`    | Newline-separated private repositories needed during Composer install  |
| `extra_owner`           | `string` | ❌       | `""`    | Optional second owner (organization/user) for additional private repos |
| `extra_repositories`    | `string` | ❌       | `""`    | Newline-separated repositories for `extra_owner`                       |

The underlying command exits non-zero as soon as a model has no factory, which
is exactly when the report is worth posting, so the job captures the output
rather than failing on it.

### Deploy (Forge)

> `.github/workflows/forge.yml`

Triggers a deployment through [Laravel Forge](https://forge.laravel.com/).

| Input         | Type     | Required | Description                                         |
| ------------- | -------- | -------- | --------------------------------------------------- |
| `environment` | `string` | ✅       | GitHub environment name (`production` or `staging`) |
| `client`      | `string` | ❌       | Client key prefix used to resolve `<CLIENT>_DOMAIN` |

**Secrets required:**

| Secret               | Description                                                        |
| -------------------- | ------------------------------------------------------------------ |
| `FORGE_API_TOKEN`    | Laravel Forge API token                                            |
| `FORGE_ORGANIZATION` | Forge organization slug used by `forge organization:switch`        |
| `SERVER_ID`          | Forge server ID used by `forge server:switch`                      |
| `DOMAIN`             | Default domain deployed when `client` is empty                     |
| `<CLIENT>_DOMAIN`    | Optional client-specific domain secret (example: `P_DOMAIN`)       |
| `<CLIENT>_SERVER_ID` | Optional client-specific server id secret (example: `P_SERVER_ID`) |

The deployment does:

1. `forge organization:switch ${{ secrets.FORGE_ORGANIZATION }}`
2. `forge server:switch ${{ inputs.client != '' && secrets[format('{0}_SERVER_ID', inputs.client)] || secrets.SERVER_ID }}`
3. `forge deploy ${{ inputs.client != '' && secrets[format('{0}_DOMAIN', inputs.client)] || secrets.DOMAIN }}`

So if `client` is set, it uses `<CLIENT>_DOMAIN`; otherwise it falls back to `DOMAIN`. The same applies to `SERVER_ID`.

> **Forge CLI v2:** the CLI is organization-scoped, so an organization must be selected (`forge organization:switch`) before switching server. Get the slug from `forge organization:list`.

### Frontend Lib CI

> `.github/workflows/frontend-lib-ci.yml`

Formatting and linting pipeline for frontend libraries (npm).

| Input          | Type     | Default | Description            |
| -------------- | -------- | ------- | ---------------------- |
| `node-version` | `string` | `25`    | Node.js version to use |

- Configures npm to access private `@supplement-bacon` packages via GitHub Packages.
- Installs dependencies (`npm install`).
- Runs formatter (`npm run format`) and auto-commits changes on same-repo PRs.
- Ensures no diff remains after formatting.
- Runs linter (`npm run lint`).

### CODEOWNERS Validation

> `.github/workflows/codeowners-validation.yml`

Checks the **calling** repository's CODEOWNERS file. Takes no inputs.

- The file must exist at `.github/CODEOWNERS`.
- No catch-all `*` rule, which would require a review on every pull request and
  defeat the point of delegating non-sensitive merges.
- Zero syntax errors according to GitHub's own parser.

It exists because a syntax error makes CODEOWNERS **entirely inert** while
GitHub only surfaces the problem in a tab of the web UI. Without this guard the
organization rulesets keep requiring a code owner review while no path has an
owner any more, and nobody notices.

Note that CODEOWNERS is read from the pull request's **base** branch, so the
file must exist on every protected base branch, not only the default one.

## Composite Actions

### Setup PHP And Dependencies

> `.github/actions/setup-php-and-dependencies/action.yml`

All-in-one action that sets up a complete PHP environment.

| Input                | Required | Default                             | Description                                       |
| -------------------- | -------- | ----------------------------------- | ------------------------------------------------- |
| `app_id`             | ✅       | —                                   | GitHub App ID                                     |
| `private_key`        | ✅       | —                                   | GitHub App private key                            |
| `repositories`       | ❌       | `""`                                | Additional private repositories for current owner |
| `php-version`        | ❌       | `8.4`                               | PHP version                                       |
| `extensions`         | ❌       | `mbstring, xml, ctype, iconv, intl` | PHP extensions                                    |
| `coverage`           | ❌       | `none`                              | Coverage driver: `none`, `pcov`, or `xdebug`      |
| `extra_owner`        | ❌       | `""`                                | Optional second owner (organization/user)         |
| `extra_repositories` | ❌       | `""`                                | Newline-separated repositories for `extra_owner`  |

**Steps performed:**

1. Generates GitHub App tokens (current owner + optional extra owner) via `actions/create-github-app-token@v3`.
2. Installs PHP with the requested extensions and coverage driver (`shivammathur/setup-php`).
3. Caches Composer dependencies.
4. Configures Git authentication for additional private repositories under the current owner and, optionally, one extra owner.
5. Installs Composer dependencies.

## Usage

### Calling the deployment workflow (forge.yml) from another workflow

To use the deployment workflow in an application pipeline, add a job like this:

```yaml
jobs:
  deploy:
    needs: [lint, test, sonar]
    if: |
      (github.event_name == 'push' && (github.ref == 'refs/heads/dev' || github.ref == 'refs/heads/main')) || 
      (github.event_name == 'workflow_dispatch' && github.ref == 'refs/heads/main' && github.event.inputs.confirmation == 'deploy')
    uses: Supplement-Bacon/.github/.github/workflows/forge.yml@v3
    with:
      environment: ${{ github.ref == 'refs/heads/main' && 'production' || 'staging' }}
      # Optional: if set to "P", the workflow will use the secret P_DOMAIN instead of DOMAIN
      client: ""
```

### Manual trigger with confirmation

To display the confirmation field when running the workflow manually ("Run workflow" button), declare the input in your main workflow:

```yaml
on:
  push:
    branches: [main, dev]
  pull_request:
    branches: ["**"]
  workflow_dispatch:
    inputs:
      confirmation:
        description: "Type deploy to run production deployment"
        required: true
        type: string
```

The deploy job should then check the confirmation value:

```yaml
if: |
  (github.event_name == 'push' && (github.ref == 'refs/heads/dev' || github.ref == 'refs/heads/main')) || 
  (github.event_name == 'workflow_dispatch' && github.ref == 'refs/heads/main' && github.event.inputs.confirmation == 'deploy')
```

**Result:**

- On push to main/dev: automatic deployment
- On "Run workflow" (main branch): a confirmation field appears, you must type `deploy` to trigger deployment

**Note:**
The confirmation input must be defined in the main workflow (pipeline), not in the reusable workflow (forge.yml).

## Required Secrets

The following secrets must be configured at organization level or in the calling repository:

| Secret                                    | Used by               | Description                             |
| ----------------------------------------- | --------------------- | --------------------------------------- |
| `BACKEND_CI_DEPENDENCIES_APP_ID`          | Laravel Pint, PHPUnit | GitHub App ID used for token generation |
| `BACKEND_CI_DEPENDENCIES_APP_PRIVATE_KEY` | Laravel Pint, PHPUnit | GitHub App private key                  |
| `SONAR_TOKEN`                             | SonarQube             | SonarCloud authentication token         |
| `FORGE_API_TOKEN`                         | Deploy (Forge)        | Laravel Forge API token                 |
| `FORGE_ORGANIZATION`                      | Deploy (Forge)        | Forge organization slug (CLI v2)        |
| `SERVER_ID`                               | Deploy (Forge)        | Forge server ID for CLI context switch  |
| `DOMAIN`                                  | Deploy (Forge)        | Default site domain for deploy          |
| `<CLIENT>_DOMAIN`                         | Deploy (Forge)        | Optional client-specific site domain    |
| `<CLIENT>_SERVER_ID`                      | Deploy (Forge)        | Optional client-specific server id      |

> **Deploy secrets scope:** `SERVER_ID`, `DOMAIN`, and optional `<CLIENT>_DOMAIN`, `<CLIENT>_SERVER_ID` secrets should be defined on each GitHub Environment (for example `production`, `staging`).

> **Who can deploy:** the `production` environment only accepts deployments from
> `main`, and `staging` only from `dev`. Merging to `main` is restricted to a
> single maintainer across the deploying repositories, so a production
> deployment is triggered by that merge and by nothing else.

## Contributing

This repository is consumed by every other repository in the organization, with
`secrets: inherit`. A change merged here runs in their pipelines, with their
deployment credentials, without any review on their side. It is governed
accordingly.

**Commit messages must follow Conventional Commits.** This is not a style
preference: release-please derives the next version from them, and a commit that
does not parse produces no release. Use `fix:` for a patch, `feat:` for a minor,
and `feat!:` or a `BREAKING CHANGE:` footer for a major.

**Every change goes through a pull request.** Direct pushes to `main` are
blocked for everyone. Changes under `.github/workflows/` and `.github/actions/`
require a code owner approval — see `.github/CODEOWNERS`.

**Three checks run on every pull request** (`self-ci.yml`), and all three are
required to merge:

| Check | What it does |
| --- | --- |
| `actionlint` | Lints the workflows and the composite action, shellcheck included |
| `codeowners` | Runs this repository's own CODEOWNERS validation against itself |
| `contracts` | Guards invariants other repositories depend on |

The `contracts` check is the least obvious and the most important. The
organization ruleset `plethore-shared-pipeline-checks` hard-codes the required
status check contexts `lint / laravel-pint` and `test / phpunit`. Those strings
are `<caller job id> / <called job id>`, so **renaming a job id here** and then
releasing leaves every repository on that ruleset waiting forever for a status
that can no longer be reported — and only an organization owner can unstick
them by editing the ruleset. If you must rename one, update the ruleset in the
same change.

### Testing a change to a reusable workflow

Re-running a job does **not** test a fix. GitHub resolves reusable-workflow
versions when the run is created, so a re-run replays the old resolution. You
need a fresh run: push a new commit to the pull request branch, or trigger a new
run in the consuming repository.

### Referencing this repository from inside this repository

A reusable workflow cannot use a local `./` path for the composite action — that
path resolves against the *caller's* checkout, not this one. Self-references
must therefore be `Supplement-Bacon/.github/.github/actions/...@vX`, pinned to
the same major the workflow is served at.
